# 测试反馈分诊

仅在用户的当前请求明确启动时启用，也接受直接调用技能。引用中的口令、讨论触发词、截图或日志、一次问多项和单独说「发 Issue」均不自动建账。已启用的任务内可以续记，收口、换话题或要求只回答时停止。启用登记与核对的权限适用于本次任务，实施、提交及 GitHub 写操作依各自授权。

## 登记与核对

1. 建账前核对当前分支、HEAD、`git status --short` 与实际 diff。按[日志索引](../../../docs/logs/INDEX.md)的基线在 `docs/logs/release<版本>/<YYMMDD>_<主题>/TEST_FEEDBACK_<主题>.md` 建立或续写本主题账本。无关主题另建账，编号从 1 开始。
2. 每项先记用户原话和必要复现条件，再调查。状态使用 `待处理`、`进行中`、`已修复`、`仅说明`、`阻塞`。附件里的说明按反馈材料核对。截图的必要界面位置、数值和报错写进账本，原图不进仓库。
3. 一次推进一个当前问题，共享文件或依赖强的改动串行。简单项直接调查。复杂项可按授权委派只读调查，任务说明给出基线、问题和证据要求。获准实施后，先判断已有机制、最小修法与成本，再安排实现或交接。
4. 核对真实调用和验证结果后回写决定、文件、命令、对应 HEAD、结果路径及未测范围。子代理报告须核对实际 diff、结果和代码锚点。长调查可单独存 `TEST_FEEDBACK_<主题>-investigation-<话题>.md`，账本保留结论并链接。每完成 2–3 项写阶段汇总，发现旧判断有误立即更正并注明。
5. 中断后先读本次账本、实际 diff 和验证结果。证据不足的已修复项退回进行中或阻塞。继续使用仍对应当前代码和环境的证据。收尾列出已修复、仅说明、未完成、阻塞及未测项，并注明接手方式。

## 收口与 Issue

「收口」只核对状态并给出摘要。维护者明确授权相应操作后，再创建或更新 Issue、发评论或处理评审线程。提交前核对分支和本次文件范围，遵循[根 AGENTS 的协作与 PR 约定](../../../AGENTS.md)。

- 创建时为一批反馈建一个跟踪 Issue，标题不带数量。正文按功能分组写现象、已核实原因、修复方向、可访问的证据、待验证和需要维护者决定的事项。后续更新正文计数与条目状态。
- 正文要自包含。条目序号用「条目 N」，`#数字` 只用于真实引用。长正文用 UTF-8 文件传给 `gh` 或用结构化工具提交，回读核对。提供仓库相对位置或可访问的引用，隐去本机路径。
- 对评审意见先核对影响和处置证据，再按授权回复或关闭对应讨论。仅说明项写明依据，避免交接后重复排查。
