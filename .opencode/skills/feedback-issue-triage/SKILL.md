# 反馈逐条核对 → Issue 交接流程

维护者实测新版本时会把问题一条条发进来。本流程的目标：**任何一条反馈都不丢失、
每条都有可信的核实结论、最终沉淀为后续 agent 可直接实施的交接文档**。
默认只核对与记录，不实施代码改动（维护者统一安排实施）。

## 核心纪律：先记录，后调查

维护者明确要求过：收到反馈**先写进账本再调查**。上下文随时可能被压缩，
账本是唯一事实源——没落盘的信息等于没发生过。

1. 每条反馈收到后，立即在账本问题清单追加一行（现象用维护者原话+补充细节），
   状态用 `待处理`；哪怕只来得及写现象也要先写。
2. 调查结论随时回填对应行；发现早前记录有错（包括自己此前的错误结论），
   **当场更正账本并在阶段汇总里注明**，不掩盖。

## 账本

- 位置：`docs/logs/release<baseline>/<YYMMDD>_<主题>/TEST_FEEDBACK_<主题>.md`。
  子文件夹用 **6 位日期前缀 + 下划线 + 主题** 命名（如 `261015_测试反馈`；维护者 2026-10-15 定的规范，
  替代旧的 `undated/` 层）。当前基线看 `docs/logs/INDEX.md` 顶部（`log-release-baseline` 注释）。
- **一账本一主题，不混杂（维护者 2026-10-15 指示）**：新反馈若与现有账本主题无关
  （例如来自另一分支/另一功能的实测），不要追加进旧账本；另建
  `<YYMMDD>_<新主题>/TEST_FEEDBACK_<新主题>.md`，编号从 1 起。同一主题的后续反馈
  继续进自己的账本。混入无关条目会淹没后续 agent 与维护者的上下文。
- 结构：头部写流程约定与状态取值（`待处理`/`进行中`/`已修复`/`仅说明`/`阻塞`）；
  正文一张问题清单表（# | 问题 | 状态 | 核实结论/方案）；尾部「阶段汇总」按时间追加
  （每闭环 2-3 项或每次调查落定写一条「续 N」，含状态变化与遗留事项）。
- 建账前先核对基线：`git status --short`、当前分支与 HEAD，写进账本头部。

## 截图

- **图片不入 git、不存仓库**。会话粘贴的截图把必要信息（界面位置、数值、文案、
  报错原文）转成文字写进对应条目；没有额外信息量的图直接忽略。
- 粘贴图落盘在用户目录（如 `~/.paseo/desktop-attachments`），需要确认细节时可以读，
  但不要复制进仓库。

## 调查分工

- **小项主会话直接查**：1-2 次搜索就能定位的（文案改写、样式类、单个函数行为），
  当场定位、结论直接入账。
- **复杂项派只读子代理**（explore）：交互抖动、跨模块链路、需要逐条件推演的。
  要点：
  - prompt 自包含：仓库路径、跳过构建产物、现象、要查清的问题清单（编号）、
    要求 file:line 证据、「只读、报告以最终回复返回」；
  - 明确写「**必须以文字报告作为最终回复，不允许空回复**」（子代理可能空返回，
    空了就原样重派一次）；
  - 多个独立调查并行派发（background），等通知期间做记录与收尾工作。

## 核对：子代理报告不可直接信任

报告回来必须抽查 2-4 处关键 file:line（rg 验证原文与行号吻合）再入账。
抽查发现不符时：修正账本结论，必要时追问或重派。
本流程实测中抽查抓出过两类问题：调查报告与实情不符的细节、以及**核对脚本自身
的错误结论**（如时区计算错、截图看错字）——核对自己的核对工具同样是流程的一部分。

## 调查报告存档

较长的子代理报告原文存为独立文档，与账本同目录：
`TEST_FEEDBACK_<主题>-investigation-<话题>.md`。账本条目里写「详见该文件」并保留
浓缩结论。这样账本精炼可扫读，细节不丢失。

## 收口：汇总为 GitHub Issue 交接文档

维护者说「发 Issue」「收口」时：

1. 用 `gh` 创建**单个** tracking issue（标题含项数），正文作为交接文档。
2. 长文本（中文 + markdown + 反引号）**一律走文件通道**：正文写临时文件
   （如 `.artifacts/<task>/issue-body.md`），`gh issue create --title ... --body-file ...`；
   后续更新用 `gh issue edit --body-file`，补充结论用 `gh issue comment --body-file`。
3. 正文按功能模块分组（A/B/C…），每条带：现象、根因、修复方向、file:line、
   需同步的测试/文档。尾部固定两节：「待维护者决策」、「实施约束」
   （bundle 重建、schema 同步、不署名等项目约定）。
4. Issue 是活文档：新反馈追加分组并更新标题计数；调查闭环时把「调查中」改为结论。
5. 本地账本通常未提交——Issue 正文要自包含，同时注明账本路径供本机 agent 深查。
6. **Issue/PR 文本不用 `#数字` 作条目序号**（GitHub 会自动链接成同仓库引用）：用「条目 N」
   等文字形式；真实的 issue/PR 引用才用 `#`。账本内的 `#N` 编号仅本地使用（不上 GitHub），
   与 Issue 的「条目 N」一一对应。

## 与维护者的沟通

- 每条闭环简短汇报：结论 + 是否需要维护者拍板（阈值、文案、取舍类决策列成清单）。
- 「仅说明」类（核实后无需改动）明确说出依据，避免后续重复排查。
- 一次性抛出所有待确认项，方便维护者集中拍板。

## 提交相关文件

维护者要求提交时：

- **先 `git branch --show-current` 确认当前分支**——共享工作区可能已被并行会话切换；
  提交落在非预期分支时如实报告，由维护者决定是否 cherry-pick。
- **用 pathspec 提交**（`git commit -F <msg文件> -- <本任务路径>`），只包含本任务文件：
  并行会话可能已把他们的 WIP add 进暂存区，裸 `git commit` 会把别人的工作卷进来。
- 提交信息走文件通道（`-F`），不附加任何 AI 署名；pre-commit 的个人路径检查
  被拦截时按提示脱敏（如绝对路径改 `~/` 泛称）后重提。
- 并行会话的暂存内容**不要动**（不 reset、不 unstage 他们的文件）。

## 收口清单

- 账本每行都有终态（无进行中/待处理悬空，或明确标注「调查在途、结果回填方式」）。
- Issue 正文与账本一致（计数、闭环状态）。
- 在途子代理的报告必须核对入账后才算收口；本会话无法等到时，在账本注明
  「调查未完成，接手 agent 需重跑」并附上原调查问题清单。
