# CI 门禁纠偏方案

状态：本地实施与独立复审完成，已交付main的PR399及2.0dev的PR398，未自动合并。日期：2026-11-17。证据见[实施账本](../logs/release1.11.3/261117_CI门禁纠偏/TEST_FEEDBACK_CI门禁纠偏.md)；远端验收以候选最新HEAD的Actions和PR正文为准，不将本机结果预写为CI通过。

维护者后续确认分别交付目标为main和2.0dev的两个PR，不自动合并。提交前同步各自PR目标分支，而不是统一合并main；2.0dev没有374完整矩阵基线，不为移植策略新增一套原本不存在的矩阵。

本次获准调整调度、阻塞语义并验证；维护者后续明确授权独立分支提交、推送并创建PR，未授权合并。不得改变远端分支规则或发布政策，不得将候选用例或目标耗时说成已经实测。

## 1. 目标与非目标

目标是让可靠、与改动风险相称的检查决定合并，让广覆盖测试继续暴露问题，但不再用整套测试的偶发异常无差别阻塞所有改动。

- 普通文档在 PR 和 main 上均不启动完整 Python、Node、媒体和浏览器矩阵。
- 应用代码必须通过稳定基础检查及已审计的相关验证，不用“未改该文件”直接证明无影响。
- 完整巡检保留真实退出码、首次失败、报告与平台覆盖；非阻塞不等于通过、删除或跳过。
- 使用现有入口、报告与测试资产，替换重复调度，不在旧 CI 外再追加一套新矩阵。
- 本轮不承诺修完全部偶发失败，不引入智能依赖图、自动归因机器人或复杂的跨提交绿灯复用。

## 2. 已核对基线

仓库实现核对于 `main@a1e88d1c`，远端当时另有文档提交 `93eab035`；相关差异不作为已实施方案。

当前 `scripts/ci_impact.py` 非 PR 一律 full；PR 按整个 PR 差异而不是最后一次提交分类。普通工程文档、计划与日志没有轻量豁免。`test-matrix.yml` 的聚合任务要求 full-tests 和 browser 所有选中单元成功；旧 Editor/Windows Preview 的非 light 运行仍保留。因此只把新增矩阵改成辅助，不能解决旧 job 继续完整执行的问题。

GitHub 只读 API 核对结果：main 的传统 branch protection 返回 Branch not protected；适用 ruleset 只有 deletion、non_fast_forward，无 required_status_checks。现阶段不应称为“某个名称带 required 的 job 已被 GitHub 分支保护强制要求”。但统一红灯、聚合及协作中的全绿要求仍可形成事实阻塞；本方案同时纠正它们。不主动新增或改变远端规则。

## 3. 目标运行与阻塞规则

| 层 | 内容 | 运行时机 | 合并语义 |
| --- | --- | --- | --- |
| 文档与配置消费检查 | 文档链接/索引、实际消费者、必要的网站或发布说明构建 | 对应文档/输入变化；轻量 CI 自检按需保留 | 所选检查阻塞 |
| 稳定基础与相关验证 | 已审计低成本单测、构建/类型/装配、数据/安全契约、已准入的相关集成/端到端用例 | 代码 PR、main 代码变更；按风险选测 | 所选检查阻塞 |
| 完整巡检 | 现有双平台全 Python/Node、required-media 与全部浏览器分片 | 保留现有每周定时；手动；经维护者明确请求的 PR | 独立报告，不传播为通用合并阻塞 |
| Windows 预览包 | 现有完整预览构建、打包与烟测 | 打包/启动/运行时相关 PR或维护者手动请求 | 候选阶段辅助；相关 PR 的异常须明确审查处置 |
| 发布验收 | 现有 release 工作流 | 获批发布 | 本轮保持既有 Windows 阻断、辅助平台警告政策 |

不会把完整巡检从每周悄悄提高到每日；频率提高需另行确认。完整运行不再自动跟随每个 PR 更新或每次 main push。高风险共享变更可由维护者要求完整运行，但不把结果自动混进所有 PR 的通用门禁。

首版只设一个逻辑合并结论，建议固定名 `Change acceptance`。它只依赖计划生成与该计划中所选的阻塞检查。完整巡检和预览包使用明确的辅助名称、独立结论，不成为该聚合任务的上游依赖。

若某条辅助失败与 PR 直接相关，必须给出修复或维护者明确的证据化处置，不能凭“辅助”自动认定可以合并。安全/丢数据等已知严重缺陷可明确冻结相关合并或发布；不让每个无关 PR 隐性承担历史缺陷修复。

## 4. 分类与稳定用例准入

### 4.1 按变更输入分类

- PR 继续使用经过校验的整个 PR 差异；不能因为最后一笔只改文档就略过该 PR 其他未验证代码。
- main push 使用事件 before/after 的可信差异；处理多提交、首次 push、缺历史和重命名，两侧路径均计入。差异不可用时不得判作文档：扩大至稳定代码检查并清晰告警，必要时要求维护者复核；不默认拉起全部不可靠测试。
- 普通 `docs/engineering/`、`docs/plans/`、`docs/logs/` 等已审计说明文档允许轻量；先识别程序输入/夹具，再判断普通说明，不能简单放行所有 .md。
- README、用户指南、网站内容按实际网站消费者检查；CHANGELOG、发布归档、离线工具说明按现有发布/工具消费者检查。修改消费者脚本、测试夹具或契约配置时选择对应代码检查。
- 编辑器、Launcher、媒体/导出、打包/运行时分别登记有限的消费者与用例映射；共享装配、依赖、锁文件、CI/测试基础设施或未知代码选择全部已准入稳定检查。无法证明的领域映射不作为跳过依据。

### 4.2 门禁准入不是按测试技术分组

不能将 `--pack common`、全部 Node 单测或整个浏览器目录直接命名为“稳定门禁”：现有这些集合仍可能启动浏览器、真实进程或外部工具。

实施的第一项产物应为逐组清单：真实 test ID/文件、保护的契约、消费者、平台、依赖、历史首次失败、预期时间、阻塞/观察及依据。优先从已有 JSON/日志提取，不为编清单先重跑所有测试。

首批候选围绕工程数据/时间单位、导入导出契约、保存失败不破坏原工程、安全路径/请求边界、构建/装配/类型检查及 CI 选测自身契约。只有完成审计才准入；本方案不声称这些现有文件中的每个用例已经可靠。

涉及受影响行为但没有可信自动化用例时，PR 明确记录缺口与针对性人工验证，由维护者作决定；不得静默省略，也不把一次通过的真实媒体/E2E用例直接升级成稳定门禁。

## 5. 如何处理不稳定项

- 有证据证明测试竞态或环境噪声的具体用例可精确退出阻塞集合，保留运行与真实失败。不得以一个文件偶发就整域永久豁免。
- 每项记录原因、关联问题、处理责任、复核日期、恢复条件；实施者给出故障修复证据及固定候选在目标平台的预先约定重复验证记录，再审核恢复。小样本全绿不是可靠性的数学证明。
- 未知失败保持“原因未确定”，不自动归为 flaky；base/head 对照仅用于诊断，不能“一次 base 通过”就断言当前 PR 引入，也不能“两边都失败”就抹去严重风险。
- 重复验证是单独的诊断证据，不替换原始首次结果，不以 retry 后通过重写门禁。原有平台不适用与弃维护 skip 规则不随本方案扩大。
- 第一阶段不新建维护系统：复用测试策略中的显式 ID 清单和现有反馈/Issue记录，先验证门禁拆分有用，再决定是否需要自动统计。

## 6. 现有文件如何调整

| 现有入口 | 拟调整 | 明确保留 |
| --- | --- | --- |
| `scripts/ci_impact.py` | 分离变更范围与运行角色；支持可信 main 差异、普通文档、代码领域和稳定检查兜底；显式版本迁移 | 基线/事件/路径校验、整个PR差异、未知输入不降为文档 |
| `scripts/test_policy.py` 及相关策略测试 | 新增独立的门禁准入/观察角色，不与现有 common/media 所属层混为一谈 | 原有发现、media归组及精确平台豁免 |
| `.github/workflows/editor-checks.yml` | 收敛为文档/消费者、构建、稳定基础与所选领域检查；拆出原完整Node及广泛E2E调度 | 对应检查的真实失败、类型/装配/安全等已准入保护 |
| `.github/workflows/test-matrix.yml` | 复用为完整辅助巡检；收回每PR/main自动全量，保留现有定时/手动；按批准机制支持特定PR请求 | 双平台完整发现、真实媒体、浏览器分片与严格报告校验 |
| `.github/workflows/pr-release-windows.yml` | 打包/启动/运行时改动或手动时构建，不再所有非light PR自动完整预览；稳定打包契约进入所选阻塞层 | 实际预览流程、完整打包与烟测能力，不复制到另一工作流 |
| `scripts/ci_matrix.py` / 报告与汇总 | 阻塞集合与辅助集合分账；只在各自范围内聚合结果和凭据，不把辅助失败涂绿 | 所选阻塞项缺报告、重复回执、错SHA、取消或意外skip必须失败 |
| 开发指南与协作约定 | 明确合并看Change acceptance及相关风险处置，不再要求每个辅助job全绿 | 真实回归处理、首次证据、独立审查及发布政策 |

计划、回执版本及所有消费者必须同时迁移，不能只改 YAML 的 if，导致聚合器仍按旧集合要求收据。辅助报告必须存入独立命名空间，不能替代阻塞层的回执。最终展示“阻塞检查通过；辅助巡检失败/未运行”，不能笼统写“全部测试通过”。

默认不用 `continue-on-error: true` 把失败转换为成功。辅助测试自身仍红，只是不在合并聚合的依赖集合内；执行预算仍有界，PR旧提交运行按现有安全机制取消，不将取消说成通过。

远端必需状态或规则变更不包含在本次自动实施授权内。当前没有required_status_checks规则；未来如需启用，应先让新结论在目标分支实际产生，再由维护者单独批准配置，避免要求一个从不出现的旧名称。

## 7. 实施顺序与批准边界

### A. 先交付清单与最小拆分

输出旧job→新角色迁移表、首批阻塞用例清单和精确文档消费者例外；经维护者确认后，在同一候选变更中完成轻量文档、稳定检查、完整巡检/预览辅助化以及聚合依赖拆分。不先撤掉所有保护，再让保护空缺等待后续建设。

不得以“先止血”为由恢复374以前已知不完整但同名的全绿口径；核心契约缺失必须明确暴露。新旧完整矩阵不同时常驻自动运行。

### B. 用受控场景证明语义，而非只等一次全绿

优先运行计划/门禁契约单测及故障注入，再按下节有限场景验证候选。真实运行需要维护者批准的候选分支/PR，不为演示自动创建多条PR或修改main。

### C. 再决定是否扩大稳定集合

在维护者认可的观察窗口记录首次结果、失败原因和关键路径耗时，再逐项晋级。扩大夜间频率、新增平台、更多自动矩阵、自动基线比较或绿灯缓存均需另案说明成本，不夹带实施。

## 8. 验收与防退化

| 场景 | 必须观察到的结果 |
| --- | --- |
| 仅工程文档/计划/日志，分别在PR与main事件 | 文档及已声明消费者检查执行；完整Python/Node/媒体/E2E不启动；main不再因non-PR一律full |
| 用户指南或发布/工具输入变化 | 对应网站/发布/工具消费者执行，不启动无关媒体/播放/拖动测试；未知文档消费者不能被当成已验证 |
| 媒体导出或编辑器代码变化 | 稳定基础与已审计相关检查执行；确实相关的验证失败阻塞，不能靠最后一笔文档提交规避 |
| 共享代码、坏diff、重命名与新增未映射测试 | 不降为文档；扩大稳定检查并报告未覆盖风险；未知test必须有明确归属决定，不能自动永久消失到观察层 |
| 注入结果错误、漏报告及辅助失败 | 所选阻塞项真实失败/缺报告/错SHA/取消/意外skip让Change acceptance失败；辅助用例故意失败只让其自身红，证据完整且不影响无关PR合并结论 |

另验证：每周定时仍完整发现并执行双平台全部集合，聚合器能发现漏分片；发布现有门槛不变；预览请求可实际生成包，未触发时说明原因。完整发现=阻塞集合与观察集合的可审计覆盖，任何未归属用例必须被发现，不能只统计已执行项来证明覆盖完整。

耗时验收先记录当前真实成本，再给候选对照：准备/下载、各检查执行、PR关键路径和runner分钟分开统计。不用某一job更快冒充总成本下降，不事先承诺未经实测的分钟数。

## 9. 风险与回滚

主要风险是领域选测漏掉依赖、稳定集合名不副实及辅助失败被人忽视；分别以未知变更稳定全集兜底、显式准入和真实结果/责任记录降低风险。放宽合并阻塞是可见的策略取舍，不声称安全性与成本同时无代价改善。

若候选漏掉关键回归，先明确冻结相关领域合并或提升对应可靠检查，再回退有问题的选择映射/版本；必要时可回退整笔CI纠偏变更。回滚不删除测试和原始证据，不使用强推或静默更改分支规则。回退到旧全量策略意味着噪声阻塞也会恢复，必须明确告知维护者。

## 10. 请求维护者批准的默认方案

建议批准A和B：收敛现有调度、设立可审计阻塞集合、文档在PR/main均轻量、每周/手动保留完整辅助巡检、预览包按相关变更或手动执行。完成后按C观察，不自动扩大范围。

本方案不请求删除测试、放宽断言、扩大skip、全局重试、改发布政策、新增远端分支保护或立即修完所有历史红灯。
