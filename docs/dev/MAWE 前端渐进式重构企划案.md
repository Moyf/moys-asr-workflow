# MAWE 前端渐进式重构企划案

## 摘要

本企划面向 `web/` 下的 MAWE 编辑器前端，目标是在**不改变现有产品行为、不更换前端框架、不破坏便携 HTML 兼容性**的前提下，逐步降低 `editor.js` 的职责密度，建立清晰的状态、命令、渲染与运行环境边界。

当前决策如下：

- 暂不迁移 React、Vue、Svelte 或其他 UI 框架。
- 暂不引入生产 npm 依赖和强制打包器。
- 保留 `web/` 作为唯一前端源码，Server 编辑器仍是主要维护和验收对象。
- 保留 `edit.py` 生成单文件 `.edit.html` / `blank-editor.html` 的能力。
- 保留现有 DOM、CSS 选择器、快捷键、工程 schema 和导出结果；重构阶段不顺带改版或增加功能。
- 采用多个小批次渐进迁移，每个批次均可独立验证和回退，禁止一次性重写整个编辑器。

这次重构要解决的是代码边界和变更半径问题，而不是用框架替换现有实现。

## 当前执行批次

这是一个长期路线图，不要求一次性投入全部预算，也不设置一次性“重写完成”日期。每个阶段先形成可回滚的代码和验证结果，再决定是否进入下一阶段。

- 当前分支：`refactor/mawe-p0-p1`
- 当前范围：Phase 0（重构基线）与 Phase 1（统一脚本装配、模块注册）
- 当前状态：实现已完成，Server / 便携页面主要定向验收通过；1 项既有 i18n 失败和 Tauri 构建环境限制待记录处理，整体批次待验收
- 当前预算：约 30–50 工时；完成后进行继续 / 调整 / 暂停评审
- 长期预算：Phase 2–3 约 60–100 工时；Phase 4–6 只有在维护压力和验证结果证明值得时才启动
- 当前不做：React 迁移、Store 全量改造、功能改版和无关 bug 修复

每个批次都应记录实际工时、变更范围、验证结果、遗留桥接和下一批进入条件。若某一阶段已经解决主要维护痛点，可以在阶段出口停留，不以完成全部路线图为目标。

## 背景与现状

截至 2026-08-13，主要前端源码规模如下：

| 文件 | 行数 | 当前主要职责 |
| --- | ---: | --- |
| `web/editor.js` | 7288 | 编辑器设置、状态、历史、字幕列表、播放、预览、导入导出、Server 交互、快捷键及启动装配 |
| `web/waveform.js` | 3635 | 波形数据、Canvas 绘制、虚拟化、布局树、拖拽、边界调整及波形交互 |
| `web/editor-utils.js` | 962 | 可在 Node 中测试的纯函数与历史栈 |
| `web/editor-i18n.js` | 665 | 中英文界面翻译与动态 DOM 文本处理 |
| `web/editor-onboarding.js` | 621 | 新手引导及其与编辑器的窄桥接 |
| `web/editor-template.html` | 876 | 页面 DOM 骨架与内联资源占位符 |
| `web/editor.css` | 1775 | 编辑器主体样式 |
| `web/waveform.css` | 741 | 波形与工作区样式 |

现有架构并非不可维护：纯函数已经逐步进入 `editor-utils.js`，波形主体由 `WaveformEditor` 封装，新手引导也通过 `MAWE_EDITOR_BRIDGE` 使用有限接口。但 `editor.js` 仍同时承担过多职责，产生以下长期风险：

1. **状态所有权不清晰**：工程数据、选择状态、当前字幕、播放状态、面板状态、脏标记和历史记录由多个函数直接读写。
2. **渲染边界偏大**：局部动作有时需要调用多个刷新函数，遗漏其中一个便可能造成字幕列表、当前字幕面板、波形标签或预览层不同步。
3. **副作用分散**：DOM、`localStorage`、File System Access API、下载、Server API、计时器和媒体事件交织在业务操作中。
4. **隐式装配顺序**：多个脚本通过 `window.*`、顶层常量和模板内联顺序协作，新增模块时容易形成未记录依赖。
5. **变更半径扩大**：实现一个局部功能时经常需要进入同一个大文件，增加回归风险和并行开发冲突。

同时也必须保护以下已经有效的设计：

- `segments` 仍是字幕真源，所有时间均为整数毫秒。
- `waveform` 是可重建缓存，不得成为工程唯一真源。
- `web/` 同时服务 localhost 页面和便携 HTML，两种形态不能形成两套业务实现。
- `waveform.js` 已是相对独立、框架无关的命令式运行时，不应仅为追求组件化而重写。
- 当前 npm 依赖仅用于 Playwright 开发测试，生产页面不依赖 npm 安装结果。

## 目标

### 主要目标

1. 让每类状态有明确所有者，业务操作只能通过显式命令修改状态。
2. 让字幕列表、当前字幕、波形、预览和工具栏通过统一失效通知保持同步。
3. 将浏览器、文件、Server 和持久化副作用与字幕业务逻辑分离。
4. 让新增或修改一个功能通常只涉及一个功能模块、相关纯逻辑和对应测试。
5. 保持现有用户界面、工程文件、快捷键、导出文件和运行方式兼容。
6. 为将来是否引入 React 提供干净边界，使框架选择不再牵动字幕核心和波形核心。

### 非目标

本轮重构明确不做以下工作：

- 不重新设计界面，不调整现有中文文案、布局、图标或快捷键。
- 不修改 `.mosp` / JSON schema，不迁移已有工程数据。
- 不改写 `WaveformEditor` 的 Canvas、虚拟化和指针交互算法。
- 不把 Server 编辑器与 Launcher 合并成单一 SPA。
- 不加入协作编辑、云同步、插件系统或新的识别供应商。
- 不以减少总代码行数作为目标；必要的边界代码和测试可以增加总代码量。
- 不在重构 PR 中夹带无关 bug 修复。若发现 bug，应先补失败测试，再单独修复或明确登记后续任务。

## 必须遵守的约束

### 产品与安全约束

- `server-editor` 继续只监听 `127.0.0.1`。
- 工程覆盖保存、备份、媒体 Range 请求和路径校验继续由现有 Server 契约负责。
- `.env`、API Key、本机绝对路径、媒体及个人工程不得进入源码、测试夹具或日志。
- Server 编辑器是主要验收形态；便携 HTML 保留兼容性，并在涉及装配、文件加载或共享编辑逻辑时执行针对性验证。

### 源码与生成约束

- `web/` 始终是唯一前端源码。
- `blank-editor.html` 始终由 `uv run python edit.py --blank` 生成，不得手改内联副本。
- 所有脚本、样式、文档与生成文件保持 UTF-8、LF。
- 在正式决定引入构建器之前，源码必须能由 Python 生成链直接按确定顺序内联。

### 行为兼容约束

重构前后至少保持以下内容一致：

- 页面 DOM 中被 CSS、测试、i18n 和浏览器自动化使用的 `id`、关键 class 与 `data-*` 属性。
- 字幕选择、拆分、合并、删除、禁用、颜色、表情包和撤销/重做语义。
- 播放、Seek、J/K/L、A/D、方向键、鼠标和波形快捷操作。
- 工作区 schema、内置工作区、布局树规范化和本机工作区库行为。
- Server 自动保存、手动保存、未保存提示、最近工程和媒体自动加载行为。
- SRT、文本、ASS、FCPXML、OTIO、去空隙媒体脚本及其他现有导出结果。
- 中英文切换、主题、设置持久化和 `file://` 降级行为。

## 目标架构

### 分层方向

目标依赖方向如下：

```text
bootstrap / compatibility bridge
                |
                v
feature controllers ------> render coordinator
                |                    |
                v                    v
commands + selectors -----> editor store
                |
                v
pure domain logic

runtime services <--------- controllers / commands 显式调用
waveform adapter <---------> 现有 WaveformEditor
```

约束：下层不得反向读取上层模块；功能模块之间不通过隐式全局变量互调。确需协作时，由命令、选择器或显式事件完成。

### 建议目录

以下名称是实施起点，可以在不破坏职责边界的前提下微调：

```text
web/
  editor-template.html
  editor.css
  waveform.js
  waveform.css
  editor-utils.js
  editor-i18n.js
  editor-onboarding.js
  editor.js                       # 最终只保留启动装配和兼容入口
  editor/
    namespace.js                  # 唯一模块注册命名空间，不存业务状态
    core/
      store.js                    # 工程态、选择态、UI 运行态的所有权
      commands.js                 # 修改工程和历史的唯一入口
      selectors.js                # 派生数据查询，不产生副作用
      render-coordinator.js       # 收集并合并局部失效通知
    services/
      settings.js                 # localStorage 与设置规范化
      project-io.js               # 工程/SRT/媒体打开与校验流程
      server-api.js               # 保存、自动保存、最近工程、工作区接口
      downloads.js                # 浏览器保存与下载适配
    features/
      cue-list.js                 # 字幕列表与原地编辑
      cue-panel.js                # 当前字幕面板
      playback.js                 # 播放器、Seek 与播放循环
      keyboard.js                 # 全局快捷键路由与焦点守卫
      preview.js                  # 字幕/表情包预览几何
      gap-remove.js               # 移除静音空隙工具
      workspace.js                # 工作区选择、导入导出与 Server 库
      stickers-colors.js          # 表情包与颜色分组交互
      export.js                   # 导出界面编排；纯生成逻辑仍放 utils
    adapters/
      waveform-adapter.js         # WaveformEditor 的唯一上层适配点
      browser-runtime.js          # window、计时器、File API 等运行环境
```

目录拆分本身不是验收标准。每个模块必须通过参数接收依赖，并且能够说明自己拥有的状态、订阅的事件、产生的副作用和销毁方式。

### 状态边界

建议把当前状态分成三类，禁止互相混存：

| 类型 | 示例 | 持久化位置 |
| --- | --- | --- |
| 工程状态 | `segments`、`workspace`、`preview`、gap remove 数据 | `.mosp` / `.json` |
| 用户偏好 | 主题、快捷键模式、波形显示设置、编辑器设置 | `localStorage` 或 Server 设置 |
| 运行状态 | 当前选择、当前字幕、弹窗开关、拖拽会话、播放帧、临时文件句柄 | 仅当前页面内存 |

`store` 可以继续使用可变数据结构，但必须满足：

- 外部模块只能通过命令修改工程状态和共享运行状态。
- 选择器只读取并返回派生结果，不修改传入对象。
- 每个命令明确记录是否写入历史、是否标记工程脏、需要刷新哪些视图。
- 高频播放帧、指针移动和 Canvas 绘制不进入通用状态广播，避免无意义全局刷新。

建议的命令结果形式：

```text
{
  changed: true,
  dirty: true,
  history: "segments",
  invalidate: ["cue-list", "cue-panel", "waveform", "preview"]
}
```

这只是内部契约示意，不要求照搬字段名。重点是让“一次修改之后需要更新什么”成为显式结果，而不是由调用者记忆多个刷新函数。

### 模块装配

在不引入打包器的阶段，推荐使用一个受控的 `window.MAWE` 命名空间注册模块工厂；业务状态不得直接挂在 `window` 上。`editor.js` 负责创建上下文、注入 DOM/运行时依赖并启动各控制器。

`edit.py` 应维护一个有序 JS 资产清单，由 Server 页面与便携 HTML 共用同一装配顺序。新增模块只修改该清单和相应契约测试，不为每个文件继续增加散落的模板替换逻辑。

若后续发现无构建装配已经成为主要维护成本，可以单独评估 esbuild 等轻量打包方案；该决定与是否使用 React 分开讨论。

## 分阶段实施计划

每个阶段建议拆成 1～2 个独立 PR。一个 PR 只处理一个边界，不同时迁移多个高风险交互域。

### Phase 0：建立重构基线（当前批次）

目的：在移动代码前固定行为与验证边界。

状态：基线已建立；性能样本待固定工程夹具后补齐。快照记录在 [`MAWE 前端重构基线.md`](MAWE%20前端重构基线.md)。

工作项：

1. 建立 `editor.js` 顶层状态、启动顺序、全局桥接和 DOM 依赖清单，并写入基线文档。
2. 把现有浏览器用例映射到关键行为矩阵，标出仅靠人工验证的区域。
3. 为脚本装配顺序、模板 token 完整性、生成页面无未解析 token 增加契约测试。
4. 记录 Server 版的基础性能样本：典型工程首次渲染、长工程滚动时 DOM 数量、连续播放时波形刷新行为。
5. 确认当前主线测试基线；若已有失败，先记录并隔离，不把它误归因于重构。

阶段出口：

- 关键行为均能对应到自动化测试或明确的人工验收步骤。
- 当前生成链和全局依赖有可审查清单。
- 不修改产品行为。

### Phase 1：统一脚本装配与模块注册（当前批次）

目的：先建立安全的“搬家通道”，之后再拆业务。

工作项：

1. 在 `web/editor-scripts.txt` 建立有序的编辑器脚本资产清单，`edit.py`、Server 和 Tauri 构建共用。
2. 将模板中的多个 JS 占位符收敛为一个由生成器提供的有序内联结果。
3. 引入只负责模块工厂注册的 `window.MAWE` 命名空间。
4. 保留 `AsrEditorUtils`、`AsrWaveform`、`MAWE_I18N`、`MAWE_ONBOARDING` 和 `MAWE_EDITOR_BRIDGE` 兼容出口，不在本阶段改调用者。
5. 更新生成契约测试并重新生成 `blank-editor.html`。

阶段出口：

- 页面行为和 DOM 完全不变。
- 调整资产清单顺序会由测试捕获。
- Server 页面和便携 HTML 使用相同脚本顺序。

当前结果：共享脚本清单、单脚本 token、`window.MAWE` 注册表、兼容出口注册和生成契约测试已实现；完整批次验收结果记录在 [重构基线](MAWE%20前端重构基线.md)。

### Phase 2：继续抽取纯逻辑

目的：优先移动低风险、可单测的逻辑，减少后续状态迁移的复杂度。

候选范围：

- 编辑器设置的默认值、读取结果规范化和数值钳制。
- 选择、相邻字幕和命令目标的计算。
- 历史快照生成与记录类型判断。
- 字幕拆分、合并、删除、分组重建的计划函数。
- 导出参数准备、文件名和时间映射等不依赖 DOM 的逻辑。
- 工作区与预览设置的纯数据规范化。

实施规则：

- 先为现有行为补单测，再移动实现。
- 纯函数不得访问 `window`、DOM、`localStorage`、媒体元素或 Server API。
- 对外返回新值或明确的修改计划；不要在工具函数中偷偷刷新视图。
- 不为了“函数纯化”复制大型工程数据；性能敏感路径先测量再决定数据策略。

阶段出口：

- 新抽取逻辑可直接由 Node 测试加载。
- `editor.js` 的业务计算明显减少，但 UI 行为不变。
- 没有新增生产依赖。

### Phase 3：隔离运行环境与 I/O 副作用

目的：把浏览器和 Server 能力从编辑器命令中剥离，形成可替换服务。

建议按以下顺序拆分：

1. `settings`：设置规范化、`localStorage` 读取/写入和不可用时降级。
2. `downloads`：`showSaveFilePicker`、Blob 下载和文件名处理。
3. `server-api`：手动保存、自动保存、最近工程和工作区库请求。
4. `project-io`：打开工程/SRT/媒体、拖放分流、未保存确认和媒体关联。
5. `browser-runtime`：计时器、URL、权限查询、目录/文件选择器等浏览器能力。

所有服务通过显式参数接收 `SERVER_CONFIG`、运行时对象和提示/确认接口。业务模块不直接拼 Server URL，也不直接判断运行形态。

阶段出口：

- Server 专属逻辑集中在服务层。
- `file://` 降级路径有测试或明确 smoke test。
- 文件加载、保存和自动保存的用户行为不变。

### Phase 4：建立 Store、命令与统一历史边界

目的：解决最核心的状态所有权和跨视图同步问题。

迁移顺序：

1. 先接管选择集合、当前字幕和活动编辑区域等运行状态。
2. 再接管脏标记和统一撤销/重做。
3. 最后迁移字幕修改命令：文本编辑、拆分、合并、删除、禁用、颜色和表情包。
4. 每迁移一种命令，都让旧入口转调新命令，确认稳定后再删除旧实现。
5. 命令返回明确的失效范围，由渲染协调器合并同一轮更新。

特别要求：

- 文本输入原生撤销与工程级撤销必须继续正确分流。
- 删除和合并必须继续维护 head/ref 分组引用。
- 波形拖拽的连续预览与最终一次提交不能被普通命令广播拖慢。
- 新动作清空 redo、撤销后 redo 可用、布局与字幕历史类型不串线。

阶段出口：

- 共享工程状态不再由功能模块任意直接修改。
- 字幕列表、当前字幕面板、波形标签和预览层由统一失效结果同步。
- 历史和脏标记的关键路径具有回归测试。

### Phase 5：按功能抽取控制器

目的：让 `editor.js` 从业务实现文件变为装配入口。

建议采用以下风险顺序：

1. 主题、设置浮窗、帮助等相对独立的 UI。
2. gap remove、预览几何、工作区等边界较清晰的工具。
3. 字幕列表和当前字幕面板。
4. 播放、Seek 与全局快捷键路由。
5. 颜色、表情包、右键菜单和跨模块命令入口。
6. 导入导出界面编排。

每个控制器至少说明：

- `init()` 时注册哪些监听器。
- 读取哪些选择器，调用哪些命令或服务。
- 响应哪些失效类型。
- 是否拥有计时器、Observer、Blob URL 或全局监听器，以及如何 `destroy()`。

迁移期间保持现有 DOM 结构与 CSS 选择器；CSS 拆分或命名整理放到控制器稳定之后，不与 JS 搬迁同批进行。

阶段出口：

- `editor.js` 只保留页面上下文创建、模块装配、启动顺序和必要兼容桥接。
- 功能模块之间没有直接读取对方私有变量。
- 全局事件监听和计时器的所有者清晰，可重复初始化/销毁而不泄漏。

### Phase 6：清理、性能复核与框架复评估

目的：删除迁移脚手架，确认重构带来真实维护收益。

工作项：

1. 删除已无调用的旧函数、兼容转发和重复 DOM 查询。
2. 审查 `window` 暴露面，只保留正式兼容桥接和模块入口。
3. 复测 Phase 0 的性能样本；对超过基线波动范围的项目定位原因。
4. 完成 Server 主流程和便携 HTML 兼容验收。
5. 更新 `docs/DEVELOPMENT.md` 中的源码地图、模块边界和验证命令。
6. 按本企划后文门槛重新评估是否需要 React；没有满足门槛时继续保持原生模块架构。

阶段出口：

- 无临时双实现或未登记兼容层。
- 重构前后的关键行为、性能和生成契约均有对照结果。
- 后续功能可以沿新边界实现，不需要回到旧的全局共享模式。

## 验证策略

### 每个批次的最低检查

根据改动范围执行，不为纯文档或纯机械改名运行无关的重型测试：

```powershell
node --check web\editor.js
node --check web\waveform.js
node --test tests\test_editor_utils.mjs tests\test_waveform_js.mjs
uv run python -m unittest tests.test_gui_web tests.test_local_editor_server tests.test_packaging_contract
uv run python edit.py --blank
git diff --check
```

新增脚本后，语法检查应覆盖资产清单中的全部 JS，而不是只检查两个历史入口文件。命令可在 Phase 1 通过小型检查脚本统一，避免清单和验证范围漂移。

### 浏览器验收矩阵

| 变更类型 | Server 编辑器 | 便携 HTML |
| --- | --- | --- |
| 纯函数、无装配变化 | 相关自动化测试 | 通常不重复验证 |
| 脚本装配、启动、模板 | 完整启动 smoke | 必须启动并加载工程 |
| 字幕命令、历史、波形桥接 | 相关 Playwright + 人工关键路径 | 阶段出口执行对应关键路径 |
| Server API、自动保存、工作区库 | 必须验证 | 不适用，但要验证降级不显示错误入口 |
| 文件打开、下载、运行时适配 | 必须验证 | 必须验证 `file://` 路径 |
| CSS/DOM 结构 | 真实浏览器布局检查 | 若共享页面受影响则验证 |

关键人工路径包括：

1. 打开工程并加载关联媒体。
2. 列表和波形选中同一字幕，播放、暂停和 Seek。
3. 编辑文本，执行拆分、合并、删除并撤销/重做。
4. 拖动字幕边界，验证最小时长、相邻边界和 items 重映射。
5. 切换工作区、保存工作区并重开页面。
6. 手动保存和自动保存，确认备份与未保存提示。
7. 导出至少一种字幕文件并核对内容和时间码。
8. 切换语言、主题和常用设置。

### 性能保护

- 波形滚动继续只创建可见行和缓冲行，DOM 数量不能随媒体总时长线性增长。
- 播放帧不得触发字幕列表或整个应用的全量渲染。
- 指针拖动只更新必要的预览元素；历史记录在手势结束时提交一次。
- 以 Phase 0 实测数据为基线；若核心场景出现可重复的明显退化，当前阶段不得合并，除非另有书面取舍。

## 风险与应对

| 风险 | 典型表现 | 应对 |
| --- | --- | --- |
| 隐式全局依赖被搬断 | 页面启动时报未定义，某些按钮静默失效 | Phase 0 建依赖清单；Phase 1 固定资产顺序并测试 |
| 只拆文件、不拆职责 | 多个文件继续交叉读写同一批变量 | 工厂显式注入依赖；Store 和命令成为唯一共享修改入口 |
| DOM 合同意外变化 | i18n、CSS 或 Playwright 找不到节点 | JS 迁移阶段不改 DOM id/class；结构变化单独评审 |
| 历史与脏标记回归 | undo/redo 错乱、保存状态错误 | 命令结果显式声明 history/dirty；先补测试后迁移 |
| 高频交互变慢 | 播放卡顿、拖拽掉帧、长工程滚动抖动 | 高频状态不进通用广播；保留 WaveformEditor 的局部更新 |
| 便携 HTML 装配损坏 | 生成文件存在未解析 token 或启动失败 | 共用资产清单；生成契约测试；阶段出口做 `file://` smoke |
| 重构与功能开发冲突 | 大量 merge conflict、行为修复混入搬迁 | 小 PR、按领域迁移；不在同一批同时改功能和搬代码 |
| 兼容层长期残留 | 新旧入口并存，实际依赖方向不清 | 每阶段列出临时桥接和删除条件，Phase 6 清零 |

## 成功标准

完成本轮重构时，应同时满足：

1. `editor.js` 成为启动和兼容入口；若仍有大段业务实现，必须能说明未迁移原因和后续归属。
2. 工程状态和共享运行状态只有一个明确所有者，功能模块不再随意跨域写变量。
3. 字幕修改统一走命令层，历史、脏标记和视图失效由命令结果驱动。
4. 浏览器、文件、Server 和持久化能力通过服务层注入，纯逻辑可在 Node 中测试。
5. `WaveformEditor` 保持独立，并通过单一 adapter 与上层交互。
6. 新增生产依赖为零，除非另有独立决策文档批准。
7. Server 和便携 HTML 仍来自同一套源码与装配清单。
8. 既有自动化测试通过，关键浏览器路径无行为回归，性能没有可重复的明显退化。
9. `docs/DEVELOPMENT.md`、生成契约测试和实际目录结构一致。

代码行数只能作为提示：理想状态下入口文件应缩减到约 1000 行以内，但不能为了达到数字而制造碎片化文件、重复抽象或隐藏依赖。

## React 重新评估门槛

完成至少 Phase 4 后再讨论 React。仅“文件很长”或“原生 DOM 写起来繁琐”不足以启动框架迁移。

当以下条件中至少两项持续成立，并有实际案例佐证时，可以提出独立技术决策：

1. 编辑器发展为多个页面或多个可独立导航的复杂工作区。
2. 多个功能需要反复复用同一套交互组件、表单校验和可访问性实现。
3. 主要缺陷持续来自复杂 UI 派生状态同步，而不是字幕算法、媒体时序或波形交互。
4. 多名开发者需要长期并行开发前端，现有控制器边界仍无法有效降低冲突。
5. 项目正式接受生产构建链，并为离线、`file://` 和单文件分发建立稳定打包方案。
6. 现有自动化覆盖足以保护渐进迁移，且迁移有明确用户价值或维护成本收益。

若届时决定采用 React，也应遵循以下路线：

- 保留纯字幕逻辑、命令层、服务层和 `WaveformEditor`，不随 UI 框架重写。
- 先选择一个隔离面板作为试点，由 React 外壳调用既有命令和选择器。
- 验证打包体积、启动时间、`file://`、i18n、快捷键和 Canvas 集成后，再决定是否扩大范围。
- 禁止一次性重写整页后再补测试。

## 长期执行方式

建议按“小批次、短分支、阶段合并”的节奏推进：

1. 每个 Phase 或一个清晰子边界使用独立 `refactor/*` 分支，完成后合并回 `main`；不保留数月不合并的巨型重构分支。
2. 每个 PR 只处理一个边界，Phase 5 的字幕列表、播放/快捷键、预览/工作区和导入导出应拆成多个 PR。
3. 阶段出口必须同时看代码、契约测试、Server 流程和便携 HTML 兼容性；任一关键结果不清楚就停在当前阶段。
4. 每个阶段合并后更新本节的当前状态和基线证据，下一阶段从最新 `main` 开始。
5. 维护者可以在任何阶段暂停；暂停不是失败，只要新功能能够沿已建立的边界继续开发。

推荐交付节奏：

1. 当前批次：Phase 0–1，基线清单、统一资产清单、模块命名空间和生成契约。
2. 下一检查点：Phase 2–3，纯逻辑与运行环境服务，预算约 60–100 工时。
3. 条件批次：Phase 4，Store、命令、历史和渲染协调器。
4. 条件批次：Phase 5，按功能控制器逐个迁移。
5. 收尾批次：Phase 6，兼容层清理、完整验收、开发文档更新和 React 复评估结论。

每个 PR 都应在描述中列明：移动了哪些职责、保留了哪些兼容接口、执行了哪些验证、仍有哪些临时桥接以及下一批的进入条件。
