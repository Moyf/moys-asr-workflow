# 后处理供应商验证门槛修复记录

分支 `fix/ai-postprocess-provider-gate`（2026-10-20）。维护者实测反馈的两个症状：

1. 本地模型（自定义接口，LM Studio，回环地址）测试连接成功后，工具箱勾选「口播整理 / AI 校对」仍被拦截，弹窗高亮 API Key 与「测试连接」。
2. 换 DeepSeek 验证后勾选成功；取消勾选再勾选，配置弹窗又弹一次。

## 根因

勾选门槛 `autoLlmReady(stepProviderId(stepId))` 依赖两组可失配的状态：

- **供应商绑定错位（症状 1，harness 确定性复现）**：门槛检查「任务记忆供应商」（`llmProviderByTask`，默认计划会把 cleanup 组种成 `deepseek`），而设置弹窗验证的是弹窗下拉里的供应商。弹窗切换供应商时 `renderProvider(..., { syncToolbox: false })` 既不同步工具箱下拉、也不写任务记忆，于是「验证了 A、拦截的仍是 B」。弹窗焦点落在 API Key（B 无 Key 且必填）与测试连接高亮，与反馈完全一致。回环地址的 custom 槽位本身允许空 Key（`postprocess_api_key_required`），不是拦截原因。
- **内存验证标记可被静默覆写（症状 2）**：`verified` 在前端是 `window.MAWLauncher.config` 里的内存副本，任何 bridge 回包都会覆写（如 `saveSettings` 写入后端 `save_postprocess_settings` 的 `verified=is_llm_verified`；后端在「保存值与文件不一致」时会失效验证且不重记录——这是有意设计，但前端没有任何提示）。缓存一旦过期为 false，再勾选就弹窗。后端指纹回路（record → 同值保存 → 保存 plan → 重启重读）经 `.artifacts` 临时脚本实证无损，问题不在持久化文件。

## 修复（均在 `web/launcher/postprocess.js`，后端零改动）

1. `openAutoStep` 拦截路径先把设置弹窗预选到门槛检查的供应商（`checkedProviderId`），保证「验证的就是拦截的」。
2. 新增 `bindPendingStepProvider`：弹窗里测试连接 / 保存（verified）成功后，把该供应商绑定到被拦步骤的任务记忆并同步工具箱下拉。
3. 新增 `confirmAutoStepCheck` + `refreshPostprocessProviderStatus`：勾选被拦时先 `get_config` 刷新权威状态，缓存过期就静默放行；后端确实未验证才取消勾选并弹配置（原有 `highlightConnection` 行为保留）。
4. `saveSettings` 成功路径补 `maybeEnablePendingAutoStep`，与 `testConnection` 对齐。
5. mock API 增加 `postprocessVerified` 跟踪，保持演示模式与刷新逻辑一致。

安全边界不变：验证状态仍只由后端指纹（`maw-postprocess.json`）裁决，密钥存储方式未动。
