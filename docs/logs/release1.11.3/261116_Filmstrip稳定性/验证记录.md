# Filmstrip 稳定性候选验证

本记录保存测试候选及其边界，不表示 #392 的 Windows CI 慢请求已被解决。候选独立于该 PR；原始日志和 trace 留在本地临时区，不提交。

## 线上现象

- [矩阵运行 43909294032 的 Windows Chromium shard 2](https://github.com/Moyf/moys-asr-workflow/actions/runs/43909294032/job/133446663984) 在 `filmstrip-real.spec.mjs` 的暂停后细网格 target 断言处超时；同 shard 其余 260 项通过。FFmpeg / FFprobe 9.0.2 安装及门禁成功。
- 原 trace 中，恢复视图请求 250ms 网格与 10 个整秒代表帧；两次控制请求中止，后续请求耗时约 6.6 秒且租约更换。观察窗口内代表帧先成为 target，细网格仍为 preview。此顺序与代表帧优先调度一致。
- 原 artifact ID 为 `14247791466`，ZIP SHA256 为 `173aa3c29dab041d08b84c258f4f902121c8c9d8fd60e2df2c0eb10082ccce1b`。trace 不含对应 FFprobe 原始输出或服务端锁等待时间，不能据此认定慢请求或缺帧的具体来源。

## 后续 Windows Node 失败

- [#395 原 head 的 Windows Node job](https://github.com/Moyf/moys-asr-workflow/actions/runs/43994902807/job/133744517389) 为 1187 项通过、1 项失败：`helpers: exit cleans up after owner exit` 解析 PID 证据时报 `Unexpected end of JSON input`。原 artifact ID 为 `14289078727`，ZIP SHA256 为 `36e3aad7d33e929d219587f8a893847a65a8b3ee66eb3f5b8bb224d852fc6639`。
- 受控对照把旧 fixture 的 PID 写入停在已 flush 的 `[`，原测试复现相同 JSON 错误。该对照证明竞态可以产生该失败；原 CI 没有记录写入时序，不能认定它必然是线上唯一原因。
- 采用 [#394](https://github.com/Moyf/moys-asr-workflow/pull/394) 的同一原子发布方式：完整写临时 PID 文件并替换目标，leaf 等待目标存在后再监听。受控实验将临时文件同样停在 `[`；此时目标不存在、leaf 等待且端口拒绝连接，释放写入后原 `helpers: exit` 测试通过，原有 PID、旁观进程和端口断言保留。
- 完整 Windows 进程生命周期套件 25/25 通过；Node 22.23.2、Python 3.14.5 与线上环境存在差异。该验证不等于整组 CI 已通过。

## 本机对照与候选

- Windows 本机使用 FFmpeg / FFprobe 9.0.2，固定同一视频并交错执行：原先通过 `tell()` 检查输出的方式分别有 2/30、2/50 次漏掉时间戳，但 JSON 仍合法；后一次 `fstat` 及管道对照均为 50/50 完整。最终 60 次交错对照中，候选和管道各 60/60 完整，复刻旧逻辑 59/60 完整。这是本机受控证据，不证明线上那次 FFprobe 输出缺包。
- 候选改用文件大小而非共享游标监控子进程输出，保留输出上限、stderr 尾部、取消与子进程回收；同时补充子进程快速退出后 stderr 仍受 8 MiB 上限约束。
- 协调解码复用已缓存的视频元数据，避免每批重复启动元数据 ffprobe；取得元数据后复核源身份及取消状态。真实 packet 时间戳探测和 FFmpeg 解码仍保留。
- 向租约操作注入一次 9.5 秒延迟可复现请求排队、中止及租约更换；细网格最终恢复，测试仍通过。播放检查改为只读的另一方案可能漏看尚未提交的播放租约，已在独立复审后撤回。
