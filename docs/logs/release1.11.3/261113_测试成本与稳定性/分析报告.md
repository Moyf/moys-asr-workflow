## 结论摘要

1. **当前 main 不是全绿**：[当前 Editor CI](https://github.com/Moyf/moys-asr-workflow/actions/runs/43381500026) 的工具页测试失败；本地也在同一位置复现。扩大的浏览器扫描另外发现5项失败，单worker复核仍全部失败。Python 全量和重建产物后的 Node 全量在本机通过。
2. **测试数量多不等于主要成本来自数量**：Python 中 2168 项单项耗时低于 10ms，合计仅约 5.64 秒；最慢 50 项合计约 145 秒。优先优化真实媒体矩阵、夹具准备和重复构建，不能按数量大砍快单测。
3. **可以 prune，但先清无消费者准备和明确重复断言**。跨平台进程回收、真实 FFmpeg/libass、导出结果和浏览器交互不能用 mock 或源码字符串检查替代。
4. **“完整测试”有三种口径**：本地 Python + Node + 全部 Playwright；日常 CI 的选定门禁；发布 CI 的平台矩阵。三者不是同一集合，更不能把并行 job 耗时直接相加当作等待时间。

**完整本地三层目前没有“跑完一遍”的有效实测值**。如只按本轮浏览器前211项终态吞吐作线性外推，1140项约21分钟，叠加Python/Node约26分钟；样本按文件顺序、包含失败等待、缺少后续fixture成本，不是可靠预测。短期排期可先预留约25–35分钟热环境窗口，但应在稳定红灯修复后实测取代预算。仓库旧文档的“全量e2e 6–7分钟”不能直接代表如今110文件、1140项的集合。

Node 首轮未重建发布变更后的 Launcher bundle，失败为新鲜度检查；重建 bundle 后重跑整个 Node 集合通过。重建的是忽略产物，不生成根目录 `blank-editor.html`。

### 不建议优先 prune 的“重复”

- Windows/POSIX 的进程树测试：同语义但不同系统机制，不是冗余。Node 中同 Ubuntu 上 debug job 与完整 unit 的重复执行可考虑**调度去重**，不删除跨平台测试。
- Preview packaging 34 项和 media 42 项虽与 full Python 重叠，但专项仅约3s/2s，还承担早失败和 required skip 语义。先做同一次报告复用评估，收益小于重型媒体与安装；不要直接移除门槛。
- cache coverage gate 只是读同一次 Python JSON，不是在重跑测试，没有测试执行成本可砍。
- Node metadata 生产侧与 Python 消费侧、mock 与真实 FFmpeg、JS逻辑与浏览器拖动/布局：是不同故障边界。
- Python 的静态模块白名单与 manifest 自洽检查并非完全等价；后者可能漏掉“两个地方一起被删”。建立独立源码覆盖后再缩减白名单。

## 5. 推荐落地顺序

1. **先恢复可信绿灯**：工具页改用固定 CHANGELOG fixture、烧录夹具补有效接线、颜色断言改用现行令牌/对比度，焦点2项核对产品契约；媒体日志等待与缩略图10053独立建回归，不用全局 retries 掩盖。
2. **消除确定的浪费**：移除已skip用例的 portable准备，loader按需编译；逐项合并已证实重复的构建/import smoke，不追求减少总数。
3. **分层而非删重型回归**：修正 FCP7真实渲染分组，PR按领域选择，main/定时/发布保留完整及跨平台验证；明确每层skip与required边界。
4. **CI调度和环境成本优化**：先测安装缓存/可复用已校验工具链，再评估同平台重复job与显式双构建。保护实际用户等待时间，不只看累计CPU。
5. **用同SHA前后对照决定是否合并**：记录本地wall、CI关键路径、skip和失败率；裁剪后对关键故障做变异负对照。未获得同等覆盖证明的项不删。
