# 浏览器测试成本：本轮实测与下一步

这是性能分析，不是已实现的加速承诺；数据来自本机Windows、Chromium、共享开发环境，不能直接当GitHub Runner基准。原始逐案数据在 `.artifacts/test-governance-261113/browser-cost-profile.json`。

## 为什么浏览器更值得优化

- 最终Python普通全量3168项约264.58秒；Node全量1173叶子约一分钟量级。
- 浏览器完整发现1143项，包含真实Server、浏览器上下文、交互、媒体准备、截图和trace；不是1143个纯函数单测。
- 原2-worker单轮在900秒仍未完成，最后启动到1052项且含9个断言失败，不能用其进度当通过数或纯执行成本。
- 改为4分片、同时2片、每片2 workers后，全部1143项执行结束，外层746.45秒：1133通过、5失败、5个既有portable跳过。该轮还不是全绿，有失败等待，不是与原配置等价的性能A/B。

## 推荐优化顺序

1. **先稳定再计时**：修正手势命中、modal就绪、真实可见布局等前置；失败的5秒等待不是正常功能成本，不以重试后绿替代原结果。
2. **按稳定历史时长分片**：先在现有4片和相同资源下平衡长尾，不把单纯增加机器数称为代码提速。新文件仍需保守纳入，完整发现与逐案集合门槛不能丢。
3. **诊断开销做受控A/B**：同一批稳定case、相同workers与环境，比较trace开/关和截图策略；`retain-on-failure`仍需预先记录成功路径，可能有开销，但本轮没有证明它是主因。关闭后会损失故障诊断，不先全局关闭。
4. **准备阶段复用不可变资源**：评估合成媒体、编译文本和只读数据。浏览器状态、编辑历史、可修改工程及样式不能跨case共享；需要修改源媒体的用例也不能共享同一inode。
5. **迁移重复逻辑矩阵，不砍真实黄金路径**：纯格式/状态/边界组合优先由Node/Python覆盖，浏览器保留真实编辑、保存重开、播放/拖动、取消和跨层集成。先证明替代覆盖等价，再移除重复E2E。

15分钟是执行预算，不是产品性能目标。维护者已表示可按需要放宽；但应区分本地整套预算与CI单分片预算，保持显式限时、进程所有权和卡死诊断。本轮单片约4–8分钟，未验证云端安装及运行总预算；不能用拉长超时替代上述优化。
