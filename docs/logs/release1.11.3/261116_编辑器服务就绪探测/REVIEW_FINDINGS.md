# 编辑器服务就绪探测：独立审查

基线 `a1e88d1c`。#389 的 Windows Chromium 分片中，两个烧录绑定用例均在服务器就绪探测阶段超时；服务器输出显示已启动且多次记录 `GET /` 200。原有探测吞掉请求错误，现有证据不足以断定此次超时的具体原因。

对于有工程的编辑器服务器，探测首页会反复构造完整 HTML，而后续阶段已经读取轻量的 `/api/startup-status` 并要求工程 `ready`。本次让第一阶段也请求该状态端点，探测超时保留最近一次请求的错误信息；保留第二阶段的 ready / error 判断、原有超时和进程清理，空白服务器及对齐服务器仍探测首页。状态就绪不代表页面可用，业务用例仍须导航页面并验证编辑器与交互。

## 对照与审查

- 受控服务器让首页响应前延迟 2 秒，状态端点立即就绪。原逻辑在 Windows 的 45 秒测试预算内失败；新逻辑通过。该对照证明慢首页能使旧探测失败，不证明它就是 #389 的实际根因。
- 改动期间一次进程生命周期测试在读取 PID 证据时遇到空 JSON：子进程可能先监听并触发清理，父进程却尚未完成写入。合成夹具现先原子发布完整 PID 文件，再让子进程监听；独立审查复核了跨平台清理边界。原始失败记录保留在本地。
- 最终版本中，两种夹具的正常启动、启动错误、包装进程退出、命令缺失、超时与慢首页对照共 11/11 通过；底层传输测试 3/3 通过。
- 原失败的两个浏览器用例双 worker、零重试共 10 次：9 次通过，均完成真实页面加载及业务断言；1 次在测试开始前等待 Chromium 启动 180 秒后失败，该本机浏览器启动问题的原因未知。另以受控 HTTP 500 替换页面：启动状态仍就绪，原业务用例的编辑器加载断言失败，未误报通过。原始 JSON、日志和 trace 保留在本地 `.artifacts/`。
- 独立审查指出并复核了 Windows 冷启动测试预算、延迟位置、启动错误断言与 PID 证据发布；修正后未发现剩余 blocker / major。

边界：新第一阶段可能比旧首页探测更早完成，因此第二阶段的 30 秒工程加载预算也可能更早开始。超慢工程加载的影响尚未实测；不得将本次对照称为 CI 原因已确认，也不得将本机浏览器结果称为全通过。
