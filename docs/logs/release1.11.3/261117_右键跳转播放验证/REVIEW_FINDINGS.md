# 右键跳转播放验证

## 首败证据

- PR 395，head `4f4ce84c`，run 44013508458 的 Windows Chromium 第 1 分片：308 通过、4 跳过、1 失败；`cue-context-seek.spec.mjs` 的实时播放位置上限为 50.5 秒，实测 50.528755 秒。原 artifact 为 14298845761。
- 原始 trace 中，首次 poll 已读到 `paused=false`、位置 50.237025 秒，处于原有 ±0.5 秒窗口；随后另一次位置读取跨约 493 ms 才结束，结果超过上限。证据支持「播放已在推进、后续采样过晚」的测试竞态，但该 trace 没有记录跳转时的精确位置，不能仅凭它证明实际 seek 的值。

## 调整与验证

- 点击真实右键菜单前，为真实 `#player` 包装原生 `currentTime` setter：原 setter 返回后立即调用原 getter 记录位置。测试还等待同一播放器的真实 `seeked` 事件并确认已播放，对同步读出的位置保留原来的 49.5–50.5 秒边界。没有更改产品代码、原 CI 超时或重试配置。
- 同步 getter 反映浏览器接受的 seek 位置，并非独立测量后续异步解码帧的最终位置；后续真实 `seeked` 事件没有与某次 setter 赋值建立严格的一一对应关系。固定 WAV 流程中未观察到其他主动 seek。独立审查未发现具体重大问题，并确认应记录这些限制。
- 原有实时取样的受控对照：临时等待真实播放推进至至少 51 秒，旧逻辑按原上限失败（`20261117T042150Z-89a566a3`）。初版用 seeked 回调采样在同样条件下通过（`20261117T042245Z-a3befe80`），但独立审查发现真实播放器前置 seeked 回调被人工阻塞 1.2 秒时，初版读取到 50.987175 秒（`20261117T042814Z-2b13d8a2`）。这些人工延迟证明可能的测试竞态，不能证明原 CI 中发生了相同阻塞。该初版已替换。
- Windows 本机、Python 3.11.15、Node 22.23.4、Chromium 151、两个 worker、零重试，按原 CI 中相邻 spec 顺序执行 click-behavior、cue-color-filter、cue-context-seek：51 项通过，136.61 秒（`20261117T043037Z-58a403fe`）。本机 Windows 10.0.26200、24 逻辑处理器；CI 为 Windows Server 2025、Python 3.11.9，环境并不完全相同。本地通过不能证明线上波动率归零。
- 固定原 CI head 及最终候选，在 Python 3.11.9、Node 22.23.4、一个 worker、零重试下对原失败测试分别执行 10 次：原版 10/10（93.47 秒，`20261117T043354Z-df65dfb1`），候选 10/10（68.91 秒，`20261117T043541Z-cd265d6c`）。两组均未自然重现原 CI 首败，这些样本不足以量化波动率。
- 在同一 Python 3.11.9 环境的一组临时探针中，等待播放推进至至少 51 秒后，旧逻辑读到 51.053508 秒并按 50.5 秒上限失败，最终候选通过；将 cue 目标人为错移 3 秒后，最终候选读到 53 秒并按原上限失败（`20261117T043710Z-12701ed4`）。临时探针、失败 trace 已留存在任务目录 `pr395-controlled-probes`，未留在工作树。
