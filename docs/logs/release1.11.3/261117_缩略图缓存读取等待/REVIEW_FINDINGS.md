# 缩略图缓存读取等待

基线：`a1e88d1c`。目标是缩小可证实的缓存读取等待，不将其当作线上失败的完整根因。

## 证据与修复

- Windows 本地使用真实 SQLite：先持有 `frames.sqlite3` 的 `BEGIN IMMEDIATE` 写事务，再读取已提交的画面和关键帧。旧逻辑在事件等待 2 秒内未完成；回滚写事务后读取结束。首败保留于本地 `run_check` 记录 `20261117T020534Z-91d922a8`。
- `_connect` 对已经是 INCREMENTAL 的数据库反复设置 `auto_vacuum` 会造成不必要的写锁等待。修复后先查询模式，仅当模式不是 2 时继续执行原有设置；新库仍初始化为 INCREMENTAL，旧版非 INCREMENTAL 布局保持原状。配额、建表和写事务逻辑未改变。
- 同一回归在新库和旧版模式 0 库均通过，能在持有写事务时读取已提交的样本与标记（`20261117T020629Z-64172fd7`，2 项通过）。
- 单独对真实 `ThumbnailJobManager.status` 做写事务对照：修复后请求到达 pin 阶段，但 pin 的真实写事务仍等待写者回滚；释放后请求成功。这是本次范围的明确边界（`20261117T020738Z-8ff3e2b5`）。
- 缓存、任务和 HTTP 服务测试共 69 项通过（`20261117T020757Z-b7496085`）。首次使用系统 Python 的同组运行因缺少 `send2trash` 导入失败（`20261117T020703Z-a13f203d`）；确认依赖锁一致后使用已有环境完成验证。个人路径检查通过。

## 空画面状态与 pin 写等待

- 后续通过真实 HTTP 和独立连接持有 `frames.sqlite3` 写事务：初始空画面、尚未有 pin 的 status 在原实现中仍同步执行 `release_owner`，2 秒内未返回（`20261117T021742Z-a2701849`）。对照中预先准备视频信息并停用后台 worker，以隔离请求链路，不代表完整生成负载。
- 新租约的 owner 从未尝试写 pin 时，没有属于它的 pin 可释放；此时跳过空释放。一旦尝试过写 pin，即使调用抛错，后续空状态也始终执行释放，已有画面的每次续租保持原语义。相同真实 HTTP 对照在写事务持有时返回（`20261117T021811Z-361ccd9e`）；缓存、任务和 HTTP 服务测试 71 项通过（`20261117T021854Z-607ae9d6`）。
- 已有画面的真实 HTTP 对照仍会在 pin 写事务等待时阻塞，写者回滚后恢复（原逻辑对照 `20261117T021352Z-3e7a7ba7`）。因此改善限于尚未尝试 pin 的空状态，并未消除所有慢请求。
- 曾试验复用未过期的内存 pin 以减少写入，但独立审查发现墙钟前跳导致另一连接清理 pin、再回拨后会错误跳过续租；配额回收可删除活跃画面。候选已撤回，独立连接实验 `20261117T021601Z-8c76478f` 与撤回对照 `20261117T021636Z-c24a6f77` 保留该证据；无法据此推断 CI 曾发生跳钟。
- 写事务范围探针以 16 张小型测试帧实测：每帧执行一次 `_evict`，总共 16 次 pin 清理、16 次候选扫描和 32 次 sample 计数；本机空缓存注册约 15.8 ms，其中 `_evict` 合计约 0.7 ms（`20261117T022007Z-05ac2a6b`）。这显示重复查询但未证明它是慢 I/O 或线上长持锁根因；清理、配额及并发回收契约不因该单次测试而改动。
