# 缩略图缓存读取等待

基线：`a1e88d1c`。目标是缩小可证实的缓存读取等待，不将其当作线上失败的完整根因。

## 证据与修复

- Windows 本地使用真实 SQLite：先持有 `frames.sqlite3` 的 `BEGIN IMMEDIATE` 写事务，再读取已提交的画面和关键帧。旧逻辑在事件等待 2 秒内未完成；回滚写事务后读取结束。首败保留于本地 `run_check` 记录 `20261117T020534Z-91d922a8`。
- `_connect` 对已经是 INCREMENTAL 的数据库反复设置 `auto_vacuum` 会造成不必要的写锁等待。修复后先查询模式，仅当模式不是 2 时继续执行原有设置；新库仍初始化为 INCREMENTAL，旧版非 INCREMENTAL 布局保持原状。配额、建表和写事务逻辑未改变。
- 同一回归在新库和旧版模式 0 库均通过，能在持有写事务时读取已提交的样本与标记（`20261117T020629Z-64172fd7`，2 项通过）。
- 单独对真实 `ThumbnailJobManager.status` 做写事务对照：修复后请求到达 pin 阶段，但 pin 的真实写事务仍等待写者回滚；释放后请求成功。这是本次范围的明确边界（`20261117T020738Z-8ff3e2b5`）。
- 缓存、任务和 HTTP 服务测试共 69 项通过（`20261117T020757Z-b7496085`）。首次使用系统 Python 的同组运行因缺少 `send2trash` 导入失败（`20261117T020703Z-a13f203d`）；确认依赖锁一致后使用已有环境完成验证。个人路径检查通过。

## 独立审查

独立审查完整代码及测试 diff，未发现 blocker 或 major。新旧库初始化、物理配额、异常处理和播放租约均保留。审查指出 manifest 读取回归不能代表 status 全链路；上述 manager 对照已记录剩余写等待。

## 未决边界
