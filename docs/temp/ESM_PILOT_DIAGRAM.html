回应 PR #157 评审：如何让 4 个真 ESM 模块安全嵌回 3 个消费端共用的经典拼接架构 —— 方案核心是「不让消费端学会打包，而是把打包结果伪装成一个普通清单条目」。

三个消费端的装配逻辑一模一样：读清单 → 把每个条目当 classic 脚本按序拼进 <script>。它们不在乎条目「是什么」——这就是方案的支点。

③ 三个消费端

零改动

edit.py / serve.py / build.rs 只是读到清单里多了一个普通 classic 脚本。不引入 Node 装配依赖，不改 2 种语言的 3 处逻辑。

3. 修复后的页面：双轨共存 浏览器视角与今天无差别；file:// 照常双击打开

<script>  editor-boot.js + editor-runtime.js（经典拼接 · 左轨） </script>
<script>  esm-bundle.js  ← 外壳：classic IIFE；内里：真 import 图 + 门面挂载 window.MaweHost（右轨） </script>
<script>  gap-remove-core.js + … 164 个经典脚本（左轨 · window.MaweHost 照读不误） </script>

产物位置 = 原四个文件在清单中的位置（editor-runtime 之后）。加载顺序语义不变；三页探针（基线 / 正式 edit.py 页 file:// / 正式 serve.py 页 http）八项检查全绿、零 pageerror。

3½. bundle 是怎么进清单的？ 没有机制，就是一次普通的文本编辑

web/editor-scripts.txt 的实际 diff（提交 0fc2e6af）

editor/boot/editor-boot.js editor/boot/editor-runtime.js -shared/host/storage.js -shared/host/files.js -shared/host/server-api.js -editor/boot/editor-host.js +# 下面一行是 ESM 试点转换集的打包产物（由 +# build-esm-bundle.mjs 生成，新鲜度测试把关） +editor/boot/esm-bundle.js shared/gap-remove-core.js

消费端视角

清单是仓库里的纯文本文件。消费端 读清单 → 逐条解析为 web/<条目>——bundle 条目和其他 169 条没有任何区别，解析成 web/editor/boot/esm-bundle.js 这个真实存在的文件读进去。

没有注入机制、没有动态生成、没有条件分支。「三端零改动」的原因就是这个动作平凡：它只是改了一个文本文件。

3¾. 产物的归宿 已提交的 bundle 是过渡脚手架，不是终点

构建产物不进 Git 是一般共识；放任 bundle 随迁移长大，会带来三类成本：大 diff 淹没评审 历史 blob 膨胀 源码/产物双份真相

消费端终态
server-editorhttp 下原生 ES modules 直接工作（classic 条目出 classic 标签、转换集出 <script type="module">）——零产物零构建
Tauri待验证 v2 协议能否以正确 MIME 提供模块文件；可行则零产物，不可行退打包
blank-editor.html唯一被迫打包的消费端（单文件 + file:// 产品约束）——bundle 与它同批在发布流程中出生、同批消费，不进开发路径，不进 Git

因此「接受 esbuild」是两个子决策：① 接受工具；② 产物住在哪（Git = 试点现状，零流水线改动；发布流程 = 终态，要求装配层一次真改动）。试点倾向 ② 为终态，两者一起提请维护者决策。

4. 门禁体系 评审三条阻断各自对应一道闸，全部非零退出语义

闸门拦什么失败退出
