# 测试治理

本页面向测试与 CI 维护者。目标是缩短一次修改到可信反馈的总时间，同时控制选测系统自身的维护成本。以下内容是维护目标与验收准则；已实现的命令与边界见[调试工作流](DEBUG_WORKFLOW.md)。

## 按模块联系选择测试

- 默认验证改动及其真实的直接、间接消费者。Python、Node、浏览器和 CI 共用影响计划；领域代码附带文档、日志或 CHANGELOG 时，取实际影响范围的并集。
- 优先利用模块导入、文件读取、夹具引用和现有装配关系。新增普通模块或测试应能自然进入发现，不要求维护者同步登记多套文件名单。
- 动态装配只补充少量明确的功能边界。区分测试实际保护的行为与顺带加载的代码，避免一个通用 helper 或整个 bundle 把局部修改扩成全应用检查。
- 文档也是程序输入。普通工程说明运行文档检查；网站、发布和工具说明分别运行实际消费者。文档扩展名不能掩盖可执行夹具或包内输入。
- 计划列出具体文件、准备需求和扩大范围的理由。无法确定的依赖先扩大到相关模块或功能；发布前等确需整体回归的场景才全量，并说明理由。普通 push 或治理修改不自动要求全量。
- 评价选测同时看正确性、无关检查数量、环境准备和总反馈时间。减少用例数不能以漏掉真实消费者为代价；增加新的规则也应有实际收益。

## 维护结构

| 位置 | 维护职责 |
| --- | --- |
| `scripts/test_impact_graph.py` | 提取导入、读取和调用关系；解析缓存按完整源码失效，不保存测试通过结果 |
| `scripts/local_test_impact.py` | 合并依赖与动态功能边界，输出具体测试文件及准备需求 |
| `scripts/ci_inputs.py` | 共享真实网站源清单与预览输入边界 |
| `scripts/test_workflow.py` | 执行计划并收集结果，复用选测判断准备依赖 |
| `scripts/ci_impact.py`、`scripts/ci_auxiliary.py` | 验证事件差异，将同一影响计划分流到有限准入和未覆盖消费者 |
| `scripts/ci_acceptance.py` | 维护已有必需准入及其证据校验 |

新增模块和测试先按现有导入、读取及功能关系参与发现；只有遇到新的动态装配方式才补相应边界。将测试升级为必需准入时，继续维护项目现有准入清单；不另建一份辅助测试登记表。

## 测试保护当前行为

测试应保护当前支持的打开、编辑、撤销、保存重开、导出、取消和失败恢复等用户行为、体验及真实代码契约。断言须有现行行为依据，不能为维护旧断言而倒改正确产品行为。

修复先复验失败项，再验证受影响范围。已确认失效的断言和退役用例可删除；同平台、配置、行为和产物已证明等效的重复执行可合并。有价值但夹具、隔离或观察时点错误的测试应修正。未判清的失败保留证据，避免因无关旧红灯扩大任务。

## 执行与结果真实性

日常 `Change acceptance` 仍验证明确准入的有限契约；按影响选出的其他消费者由独立辅助检查验证。报告应分别说明准入和辅助范围。辅助失败保留证据并分诊，不能将有限准入成功描述成完整产品回归成功。完整 Editor、Windows 辅助检查和正式发布保持各自入口。

必要全量应尽量完成所有独立组，保存真实退出码与完整失败清单，最后统一失败。前置准备失败只阻塞实际依赖组，其他独立组继续。终端摘要不代替完整错误记录。

本次执行、复用、失败、阻塞和未运行应明确区分。缺报告、额外跳过、超时和预算耗尽不能冒充完整通过。本地通过不代表 GitHub CI、安装包或人工体验已经验收。

接续应从完整文件或独立分组边界恢复，中断中的单元使用干净夹具重跑。复用前核对代码、测试、夹具、配置、工具链及输入，受影响旧结果失效。文件级接续和跨提交复用仍待验收。
