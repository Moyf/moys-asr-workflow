# 测试可靠性：先保护用户，再减少误报

适用范围：MAW 的单元、服务和浏览器测试。本文是写法指南，不是“全部 CI 已修复”的声明。

## 先问：这个测试保护谁？

优先保护 **打开 → 编辑 → 保存 → 重开 → 导出**，以及操作失败后工程不丢失。
测试名称应能回答：“用户做了什么，应该看到或保留什么？”

- 普通流程用真实入口、真实保存和实际输出证明结果。只看到按钮或成功提示还不够。
- 少见但可能丢数据的场景值得保留。例如切换失败后仍能保存原工程。
- 单纯算法或格式规则放在较低层测试。不要为每个内部实现细节重复启动浏览器。
- 一条测试不要混入不相关的布局、文案和保存检查。失败时应能看懂哪个行为坏了。

## 写测试时，重点做这几件事

| 容易踩的坑 | 更可靠的做法 | 对用户的价值 |
| --- | --- | --- |
| 等固定几百毫秒，就认为字体或布局好了 | 等字体信息就绪；用可重试断言等待目标布局；操作前确认元素可操作 | 慢机器不再因猜错时间报错 |
| 初始字号与结束字号来自不同字体状态 | 在同一字体就绪状态下取基准，再保留严格比较 | 真字号回归仍能被发现 |
| 多个测试共用会被修改的工程、预设或配置 | 写操作使用独立临时目录和配置；只读夹具可共享 | 单独通过的测试不再因前一条留下状态而失败 |
| 为隔离而关闭真实 autosave | 隔离文件与配置，保留产品保存机制；用可控步骤触发保存交错 | 能发现真实的保存覆盖和丢数据风险 |
| 短视频在等待响应时已经播完 | “仍播放”用足够长的媒体；“自然结束”另测，并明确控制响应到达顺序 | 不把正确的暂停状态误判成产品错误 |
| 一次慢请求只能碰运气复现 | 用闸门延迟指定响应，确认中间状态，再放行；保留原始结果断言 | 在较少运行中稳定验证真实竞态 |
| 失败就加重试、延长 sleep 或放宽断言 | 先保留首次失败证据，区分等待条件错误与产品错误 | 不把真实问题藏成绿灯 |

不是所有 `sleep` 都要机械替换。延迟本身若是测试输入，可以保留并说明目的；
不能把它当作“字体、服务或页面已经准备好”的证明。

配置隔离也不要求所有测试都独占一个服务。只有读写边界需要独立时才拆分。
已发现共享状态，不等于已证明它造成某次 CI 失败。

## 看见红灯，先定位失败阶段

| 类别 | 判断依据 | 应怎样处理 |
| --- | --- | --- |
| 产品行为错误 | 用户结果不符合契约；可控回归能在旧实现失败 | 修产品，保留能证明修复的回归 |
| 测试假设错误 | 产品行为正确，测试等待、夹具或预期不成立 | 修测试设置，不削弱用户结果断言 |
| 环境或安装失败 | 已确认的依赖下载或权限失败，业务断言未执行 | 修准备步骤；不能声称功能测试失败或通过 |
| 证据不足 | 启动超时或只有错误摘要，没有足够上下文 | 补诊断，再定位；不要凭名字归因 |

“改动没碰这个文件”不能证明红灯是随机的。新分片顺序、资源竞争、共享状态、
原有缺陷及新增测试错误都可能暴露问题；这些只是排查方向，不是现成结论。
汇总门禁失败、报告缺失往往是上游失败的后果，不应重复算成多个产品故障。

### 第一次失败就留下证据

保留提交 SHA、运行与 job 链接、平台、worker / shard、完整测试名、首次错误、
报告、服务输出和 trace。记录测试到底有没有执行到用户操作。
运行器与报告入口见[分层调试](../INDEX.md#engineering-debug)。

本地通过只能证明本次代码与环境下通过。与 CI 比较时，同时核对依赖、系统、
媒体工具和并行度。固定提交后可做少量单 worker / 双 worker 重复运行，
记录首次失败；不要拿一个 spec 的通过率当作全仓波动率。

### 服务探活要能解释失败

服务输出“started”或访问日志出现 `GET 200`，不等于客户端探活已经完成。
失败诊断应保留最后一次 HTTP 状态、网络异常、探测阶段、耗时和子进程退出状态。
对外日志不要带凭据或私人路径。不要吞掉异常后只剩一句“服务未响应”。

浏览器 trace 不一定包含 Node 侧的探活请求。缺少浏览器网络记录不能证明服务
没有收到请求。进程回收仍按[服务生命周期](../INDEX.md#engineering-e2e-lifecycle)处理，
只清理本次启动的进程。

### 新增测试也要遵守现有契约

直接调用底层构建器时，先满足它的字体等就绪前提。不要为旧测试移除产品保护。
工程切换走真实解绑入口，不要修改只读的绑定序号来模拟切换。
对整页 HTML 或大容器做 Python 断言时，按根 `AGENTS.md` 使用
`CompactContainerAssertions`。漏掉现有混入会触发确定性的规范检查失败；
这类新增测试错误不是波动性，也不是被测功能故障。

以下记录用于解释上述规则；不是滚动 CI 状态面板。

| 事例 | 已知事实 | 不应得出的结论 |
| --- | --- | --- |
| #384 字体与保存 | 字体别名迟到会改变测量基准；拖动时保存会提交旧面板 duration。保存保护有移除后失败的对照。见[核验记录](../logs/release1.11.3/261116_PR384_保存与字体同步/REVIEW_FINDINGS.md)。 | 不能靠关闭 autosave 解决保存回归 |
| #384 截帧与焦点 | 4 秒短片可能在响应前结束。预设迟到重建焦点节点有确定性回归；原 CI 缺 trace，不能认定唯一根因。见[核验记录](../logs/release1.11.3/261116_PR384_输入焦点与截帧状态/REVIEW_FINDINGS.md)。 | 不能把所有超时归为机器慢 |
| main 安装 FFmpeg | [运行 43880995977](https://github.com/Moyf/moys-asr-workflow/actions/runs/43880995977) 的首次 Windows 安装遇到 HTTP 504，测试未开始。 | 不是 FFmpeg 渲染断言失败，也不是用户功能已坏 |
| #389 服务就绪 | [运行 43899907103](https://github.com/Moyf/moys-asr-workflow/actions/runs/43899907103) 的两条媒体替换用例在 `startServer` 探活超时；服务日志已有 `GET 200`。错误被吞掉，缺少 Node 探测明细，原因仍未确定。 | 不能断言端口冲突、媒体替换错误或具体连接/响应取消问题 |

#389 中，服务写出 200 日志不能证明 Node 已收到响应头或完成响应正文处理。
下一步是补齐探测阶段的证据，而不是直接扩大启动超时。

CI 对齐发行包 FFmpeg 版本、校验和缓存的改动仍在独立开发中，本文不宣称已经落地。
目标是 CI 使用与发行包一致的版本；缓存命中后仍校验版本与必要能力。
缓存只减少重复下载，不能代替正确性验证，也不能消除其他 Setup 耗时。
本指南不调整测试范围白名单、矩阵数量或合并策略。

## 提交前的五个问题

1. 我能用一句话解释这个测试保护的用户行为吗？
2. 等待依据是实际状态，还是时间猜测？
3. 写入的工程和配置会影响下一条测试吗？真实保存还在吗？
4. 回归是否在缺少修复时失败？原有关键断言是否保留？
5. 首次失败能留下足够证据吗？未验证部分是否写清楚？
